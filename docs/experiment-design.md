## 1. 实验目的

测试用例生成既涉及需求理解，也涉及场景识别、步骤组织和预期结果表达。模型输出能够通过格式校验，并不意味着已经覆盖需求中的业务规则；人工审核记录能够保存，也不意味着实际修改负担已经降低。因此，需要在相同需求和评价条件下开展对照实验。

本实验旨在**验证所提出方法在测试用例生成质量和人工修改成本方面的表现**，并观察其运行成功情况、耗时和 Token 消耗。研究对象是大语言模型辅助生成系统的实际辅助价值，不比较“大模型与人工谁更强”，不预先认定系统优于所有生成方法。

实验与论文目标的关系是：用可追溯的生成记录和审核证据，判断当前系统是否能够提供较完整、可整理为正式用例的草稿，并说明辅助收益及其工程代价。人工仍负责判断用例是否符合需求。

## 2. 研究问题（Research Questions）

### RQ1：结构化生成流程是否能够提升测试场景覆盖能力？

对同一需求，比较普通 LLM 生成方法与当前系统方法在**人工修改前**对正常、异常、边界场景的覆盖率，以及统一的人工质量得分。

覆盖判断依据预先编写的参考场景和实际用例内容，不以模型输出的场景标签或系统规则分代替。该问题评价整套结构化生成与约束方法，不能由此单独证明某一个模块的贡献。

### RQ2：系统生成的测试用例是否能够降低人工修改负担？

在相同接受标准下，比较两组草稿的人工修改率、平均修改字段数量、直接接受率、总接受率和拒绝率。Proposed 使用现有 ReviewRecord 与草稿状态，Baseline 使用同口径的离线审核表。

上述指标衡量内容整理负担，是人工成本的代理指标。当前没有人工编辑起止计时，不能据此宣称“节省了多少分钟”或“人工效率提高了多少倍”。需要结合接受数量和覆盖情况解释，避免将少生成、少修改或直接拒绝误认为成本改善。

### RQ3：当前系统是否具备本实验范围内的工程可用性？

以 Proposed 的 GenerationRun 为主要来源，统计生成成功率、未终结记录数、平均生成耗时、实际 Token 消耗及已记录的失败类别。

成功指结果通过校验并完成系统保存，不等于用例语义正确或软件测试通过。该问题考察小规模实验中的运行表现，不推断生产环境稳定性。

## 3. 实验总体流程与控制变量

### 3.1 总体流程

```text
需求数据集（冻结需求及独立参考场景）
    ↓
Baseline 方法生成
    ↓
Proposed 方法生成
    ↓
结果保存（保留未经人工修改的初始结果和调用元数据）
    ↓
人工评价（先盲评质量，再按统一标准审核与修改）
    ↓
指标统计（质量、修改负担、工程表现）
    ↓
结果分析（按需求配对，报告收益、代价与失败）
```

上图表示每条需求需要完成的环节，不规定所有需求都先运行 Baseline。正式实验采用预先登记的交替顺序：14 条需求按 Baseline→Proposed，另 14 条按 Proposed→Baseline，并使各需求类别中的两种顺序数量相同。两组使用独立上下文，不将另一组的结果作为输入。

主实验采用 **28 条需求 × 2 种方法 × 每种方法 1 次生成**，计划共 56 次模型请求，其中 Proposed 28 次。每次提示均要求生成 3～6 条简洁用例；若均符合数量指导，预计每组有 84～168 条草稿。实际数量必须据实统计，不能为了整齐而截断、补齐或删除结果。数量指导不是现有 Schema 的硬性下限或上限。

每条需求单独建立 Proposed Session，主实验不向同一 Session 追加生成。一次调用就是一次尝试，关闭隐式重试，不在看过结果后选择多次调用中最好的结果。异常后的诊断或补跑如后续获准，另存记录，不替换主实验首次尝试。

### 3.2 控制变量

| 控制项 | 约定 |
| --- | --- |
| 模型 | 两组使用同一 DeepSeek 请求模型标识和相同服务端点；返回模型仅在有独立响应证据时确认 |
| 输入 | 相同标题、相同需求文本及业务约束；固定需求版本和文本 hash |
| 调用设置 | 相同输出 Token 上限、超时、非流式方式、关闭 thinking、无隐式重试 |
| temperature | 当前 Proposed 未显式发送，实验两组均不发送；记为 null，不解释为 0 |
| 生成数量 | 两组均提示 3～6 条；保留偏离数量指导的结果并报告实际数量 |
| 评价 | 相同参考场景、字段口径、评分表、接受标准和审核截止时间 |
| 实验环境 | 同一运行环境、相近运行时段；登记代码版本及未提交源代码摘要 |

方法差异包括 Prompt 内容、测试点显式输出、JSON 模式、Schema 验证、规则评分和系统审核流程。Baseline 的普通文本输出与 Proposed 的 JSON 约束属于被比较方法的一部分，不宣称只有一个变量不同。

正式运行前在实验清单中冻结具体模型和调用参数。现有配置支持指定超时及输出预算，但成功 Smoke 的 8,000 Token / 60 秒是局部设置，常规默认值为 2,000 Token / 20 秒，不能直接将二者视为相同配置。本方案不调整配置；后续正式执行时统一记录实际采用的参数，不按需求临时调参。

请求模型从冻结清单取得。现有 GenerationRun.provider_model 可能来自响应，也可能来自配置回退，仅凭这一字段无法判断来源；没有独立响应证据时，returned_model 记为 null，并注明“现有字段无法区分响应与配置回退”，不能直接写成“模型未返回”。后续如在实验侧安全采集 Provider 已有的响应元数据，才可据此确认实际返回模型；这项采集尚未实现，不改动业务记录。若发现返回模型变化，单列该批次并说明配对有效性，不将不同模型结果合并为同模型结论。

## 4. 实验数据集设计

### 4.1 规模与来源

拟人工编写 28 条虚构的软件需求，属于本科可完成的对照实验规模。仅使用 Demo、Sample 或虚拟系统语境，不使用公司真实需求、实习项目需求、商业数据、运行日志或缺陷信息，也不从当前项目历史业务记录抽取实验需求。

表 1 为需求类别分配，仅设计类别及数量，本轮不编写具体需求条目。

| 类别 | 数量 | 主要规则类型 |
| --- | ---: | --- |
| 用户认证 | 4 | 必填输入、长度约束、锁定或状态条件 |
| 信息管理 | 4 | 新增与修改、唯一性、必填或长度约束 |
| 查询搜索 | 4 | 查询条件、无结果、分页或范围限制 |
| 文件上传 | 4 | 类型与大小、空文件、合法与非法输入 |
| 权限管理 | 4 | 角色操作、越权拒绝、权限范围限制 |
| 订单流程 | 4 | 虚拟订单状态、数量限制、非法状态转换 |
| 系统设置 | 4 | 配置保存、取值范围、非法配置处理 |
| **合计** | **28** | 使用显式规则构造正常、异常和边界场景 |

这里的“订单流程”等类别是虚构需求主题，不要求当前系统实现相应被测业务，也不执行真实订单、上传或权限测试。

### 4.2 单条需求内容

每条需求保存稳定的 requirement_id、类别和标题，并包含：

1. 功能描述：用户执行什么操作，系统应提供什么结果。
2. 业务规则：状态条件、唯一性、顺序或其他业务判断。
3. 输入约束：类型、必填项、取值范围、数量或长度。
4. 异常条件：非法输入、禁止操作及对应处理结果。
5. 边界条件：明确的上下限、阈值及端点行为。

需求文本建议为 200～800 字，并遵守当前输入 Schema 的 20～2,000 字符范围；标题不超过 200 字符。两组使用同一规范化文本，保留原文，不因结果差而追加规则。

每类四条需求兼顾较简单的输入规则与包含状态或组合条件的规则。需求应能够从文本确定预期结果，不借助商业背景知识，也不故意保留会使评价无法判断的歧义。

### 4.3 独立参考场景

在生成之前，为每条需求编写 **6 个参考场景点：正常 2 个、异常 2 个、边界 2 个**，全体计划 168 个参考点。每个参考点记录 point_id、类别、触发条件或输入、预期行为及对应需求依据。

参考点应尽量原子化：能够独立判断某个具体输入或状态是否被覆盖。边界点必须落实到端点或临界值，不能只写“测试边界”。重复的条件不重复计分；一条用例可以覆盖多个不同参考点。

由第二名评价人员检查参考清单是否与需求一致，然后在运行前冻结。参考清单仅用于评价，**不提供给任一生成方法**；两组均只看到相同需求文本。不得在查看输出后按某一组的特点修改覆盖分母。

## 5. Baseline 方法设计

### 5.1 方法定义

Baseline 表示一般的直接提示生成方式：

```text
相同需求文本与标题
    ↓
简单 Prompt
    ↓
与 Proposed 相同的 LLM（一次调用）
    ↓
普通文本测试用例
```

拟使用 baseline-v1 的公开实验提示模板：

> 请根据以下虚构软件需求生成 3～6 条简洁测试用例，每条说明编号、标题、模块、优先级、用例类型、场景类型、前置条件、测试步骤和预期结果，以清晰列表输出。标题和需求如下。

固定要求九个内容字段是为了使人工整理任务可比，不要求模型遵循系统 JSON Schema，不提供 JSON 示例、字段枚举或测试点分析步骤。

Baseline 不使用测试点提取、系统结构化 Prompt、JSON/Schema 强制约束、自动质量检查或系统人工审核工作流。不把普通输出描述为必然低质量；其实际表现由实验评价确定。

### 5.2 采集与评价边界

当前系统没有切换为 baseline-v1 的业务入口。后续 Baseline 通过独立的单次模型调用或受控实验记录方式采集，不更改现有 Provider，不伪装为系统生成草稿，也不将其写入 GenerationRun 或 ReviewRecord。

Baseline 不使用系统审核流程，是指其生成方法不包含这一产品工作流；**为完成对照实验，仍须对输出开展同标准的离线人工评价与整理**。这属于实验评价，不是给 Baseline 增加 Proposed 的生成模块。

保留经过安全检查的生成内容，按九个字段进行不改变语义的转录。缺失字段记为空，不能在转录时补写步骤、预期结果或场景。仅版式调整和字段标签映射不计修改；补充缺失内容或改变字段值必须计入人工修改。无法可靠拆分的内容记录为不可解析，并保留可安全保存的原始生成文本。

两组的最终接受门槛统一参照当前 DraftEditInput：编号为 3～80 字符且满足 ^[A-Z][A-Z0-9_]{2,79}$；优先级为 P0～P3，用例类型为 checklist，场景类型为 normal、negative、boundary、compatibility、recovery 或 security。标题及模块必须非空并分别不超过 200、80 字符，步骤与预期必须非空且不超过 4,000 字符；前置条件可为空，但明确执行所需条件的质量标准不因方法而变。

运行前冻结无语义转换表：去除首尾空白、编号转大写、字段标签转换，以及“检查清单→checklist”“正常→normal”“异常→negative”“边界→boundary”“兼容→compatibility”“恢复→recovery”“安全→security”等一一对应显示值转换。原文、规范化值及转换记录均保留；不将“高优先级”等无法唯一对应的值自动推断为 P0/P1，不自动补默认值。两组使用同一规则；上述转录不计内容修改，超出转换表的补写、纠错或改值计入 edit。该指标因此不衡量版式转录成本。

统一字段规范是人工评价时的接受标准，不作为 Baseline 生成后的自动过滤流程。Baseline 不合法或缺失字段保留为初始缺陷，交由审核修改或拒绝，不能先丢弃困难样本。正式实验计划使用隔离 Demo 实验库，每条需求对应独立、初始没有正式用例的现有 Version，避免历史编号冲突导致额外修改；Baseline 在离线表中模拟同样的批次内编号唯一性标准。批次内重复编号如需改写，两组均记录有效修改，不在导出时悄悄改号。本轮不创建实验库、Project 或 Version。

## 6. Proposed 方法设计及模块映射

### 6.1 方法流程

当前方法的逻辑流程为：

```text
需求输入与安全、范围校验
    ↓
结构化 Prompt：要求分析测试点并组织用例
    ↓
一次 LLM 调用：联合返回测试点、用例草稿和限制说明
    ↓
Schema 验证与安全检查
    ↓
本地规则质量评分
    ↓
保存 Session、Draft 和 GenerationRun
    ↓
人工审核：修改 / 接受 / 拒绝，并保存 ReviewRecord
    ↓
接受后创建正式 TestCase（初始业务状态为 draft）
```

“测试点分析→结构化生成”是提示任务的逻辑组织。当前实现没有独立的测试点分析模型调用，也没有先保存测试点再进行第二次模型生成。不能在论文中写成已实现的多阶段模型编排。

当前 Prompt 版本为 test-design-v3（Step 3-C 只补充已有字段约束的明确说明，历史 v2 保留；Schema、评分及评价口径未变）；Provider 使用 JSON 模式，Pydantic 执行字段及结构验证。提示指导生成 3～6 个测试点和 3～6 条草稿，Schema 实际允许每类 1～20 项。规则评分主要检查结构、场景标签、步骤形式和预期结果中的可观察词，不验证真实语义覆盖，不自动修复或补生成缺失场景。

### 6.2 现有实体职责

| 实体 | 实验中的实际作用 |
| --- | --- |
| TestDesignSession | 保存需求上下文、测试点、限制说明、当前规则分和会话状态，组织草稿及生成历史 |
| TestCaseDraft | 保存九个可审核内容字段、pending/accepted/rejected 状态、来源 generation_run_id 和正式用例关联 |
| GenerationRun | 追溯一次生成尝试的输入、Provider/模型、Prompt 版本/hash、需求 hash、状态、时间、Token、错误和通过校验的结构化快照 |
| ReviewRecord | 保存真实审核用户、动作、前后快照、变化字段及数量、评论、时间和前后 Session 规则分 |

初始生成质量以该 Run 的 structured_output_json 为准，不能用人工修改后的草稿代替原始输出。失败若没有 Session，仍可由 Run 输入快照定位需求；未通过 Schema 或安全检查的模型原文不保存在该快照中。

同一 Session 可以累计多批草稿，Session 当前分及 ReviewRecord 的 score_before/score_after 描述整个 Session 的规则分。本实验使用每需求一次独立生成，并仍以 Run 筛选来源，不将 Session 当前内容误当某次调用的初始结果。

## 7. 评价指标设计

### 7.1 通用统计原则

以“需求 × 方法”的一次生成作为质量比较单位，以来源草稿及审核事件作为修改负担统计单位，以 GenerationRun 作为 Proposed 工程统计单位。

所有比例同时报告分子、分母和百分比，所有均值同时报告样本数。零分母记为 N/A；现有 review_metrics 在零分母时返回 0.0，实验表必须结合计数解释为“无可评价样本”，不能直接写成真实的 0% 修改率或拒绝率。

Mock、FakeClient、历史 Smoke、来源为 null 的历史草稿和本次正式 DeepSeek 结果分别处理。主实验只纳入预登记的正式需求与首次尝试，不将工程测试样本当作真实模型实验样本。

### 7.2 A 类：测试用例质量指标

#### （1）正常、异常、边界场景覆盖率

对需求 i、方法 m、类别 t，记参考点集合为 R(i,t)，被用例覆盖的不同参考点集合为 C(i,m,t)：

```text
类别场景覆盖率(i,m,t)
  = |C(i,m,t)| / |R(i,t)| × 100%

单条需求总体覆盖率(i,m)
  = 三类已覆盖参考点数之和 / 6 × 100%
```

“覆盖”须同时满足：用例明确涉及该参考条件，步骤能触发条件，预期结果与需求一致。仅有 negative/boundary 标签、提及“错误输入”或“边界测试”不计覆盖；相同参考点被多条用例重复描述仍只计一次。参考之外的合理扩展另作备注，不增加冻结分母。

主结果报告 28 条需求的类别覆盖率和总体覆盖率均值，并按需求类别展示。未形成可交付用例的首次尝试，其**交付场景覆盖率计为 0**，包括失败、不可解析和截止时未完成的任务，同时列明原因。这是交付层面的零覆盖，不能解释为已测得失败模型响应的语义质量。

另报告两种方法均形成可评价输出的配对需求上的覆盖率差值及样本数，说明成功样本条件下的表现。人工质量得分缺失记 N/A，不将不可读取输出伪造为人工打分样本。

#### （2）10 分制人工评价

评分对象为每条需求对应的**初始用例集合**，两名评价者分别在五个维度给出 0、1、2 分，合计 0～10 分。

| 维度 | 0 分 | 1 分 | 2 分 |
| --- | --- | --- | --- |
| 测试目标完整性 | 未体现主要功能目标或与需求冲突 | 体现部分主要目标但有遗漏 | 正常参考点均有对应目标，且未增加与需求冲突的目标 |
| 测试步骤可执行性 | 可执行用例不足一半 | 至少一半可执行，仍有明显缺失 | 所有用例的前提、输入和动作足以支持执行 |
| 预期结果明确性 | 明确且正确的预期不足一半 | 至少一半明确且正确，仍有笼统或冲突表述 | 所有预期均可观察、与需求一致，足以判断结果 |
| 异常场景覆盖 | 0/2 个参考点覆盖 | 1/2 个参考点覆盖 | 2/2 个参考点覆盖 |
| 边界场景覆盖 | 0/2 个参考点覆盖 | 1/2 个参考点覆盖 | 2/2 个参考点覆盖 |

步骤“可执行”是文本评价，要求前提、输入和操作足够明确；本实验不运行被测业务，不能称为执行成功。空的用例集合不进入人工评分。

两名评价者总分取算术平均，保留原始维度分及理由；再报告每种方法的均值、中位数和范围。系统 0～100 规则分作为辅助描述单列，不换算成这里的 10 分制，也不使用 ReviewRecord 中的规则分充当人工评分。

### 7.3 B 类：人工成本代理指标

九个内容字段为 suggested_code、title、module、priority、case_type、scenario_type、precondition、steps、expected_result。一次修改中某字段值发生变化计 1，最多 9；字符数和改写长度不参与计数，status、accepted_test_case_id 和时间等元数据不计修改。

对一个方法的来源草稿集合 D，N=|D|。令 E 为 action=edit 且 changed_field_count>0 的修改事件集合：

| 指标 | 计算口径 |
| --- | --- |
| 人工修改率 | 至少有一次有效修改的去重草稿数 / N |
| 平均修改字段数量 | E 中 changed_field_count 之和 / 有效修改事件数 |
| 总接受率 | 截止时 accepted 草稿数 / N，包含修改后接受 |
| 直接接受率 | accepted 且有接受证据、接受前从未发生有效修改的草稿数 / N |
| 拒绝率 | 截止时 rejected 草稿数 / N |
| 待审核率 | 截止时 pending 草稿数 / N |

平均修改字段数量沿用现有 review_metrics：分母是**有效修改操作次数**，不是全部草稿数。同一字段在两次修改中变化两次，计两次；同一草稿多次修改在人工修改率中只计一条。可补充报告“累计字段变化次数 / N”，帮助观察全部草稿的平均整理负担，并明确其与上述指标不同。

无变化 edit 计审核事件，不计修改，也不影响直接接受判断。改过再恢复原值仍属于修改。接受动作不等于直接接受；直接接受率当前可由审核链离线派生，页面函数未直接返回该指标。没有完整审核链的历史数据不能据“没有 edit”推断直接接受。

Proposed 来源为 Draft.generation_run_id 对应的草稿、ReviewRecord 的 action/changed_field_count/快照及 Draft.status。Baseline 用离线审核事件表保存同样的字段变化、动作和终态；缺乏审核记录时记为未采集，不能填成 0% 修改或 100% 直接接受。

两组均审核到接受或拒绝为止，并在固定截止点汇总；未完成部分保留 pending。接受、拒绝、待审核率之和应为 100%，修改率与它们不构成互斥分区。结果同时列出生成草稿数、接受数、拒绝数和最终覆盖率，防止只因大量拒绝就得到“修改少”的表面优势。

### 7.4 C 类：工程指标

Proposed 直接使用预登记 GenerationRun。令 S 为 succeeded 数、F 为 failed 数、U 为截止时 running 数：

| 指标 | 计算及来源 |
| --- | --- |
| 已终结生成成功率 | S / (S+F)，同时报告 S、F、U |
| 计划任务交付率 | S / 28；未开始、调用前失败及未终结任务另列，不从计划中删除 |
| 平均生成耗时 | 成功 Run 的非空 latency_ms 均值，单位 ms；失败耗时单独汇总 |
| Token 消耗 | 分别统计非空 prompt_tokens、completion_tokens、total_tokens 的均值和已知值总和 |
| 失败类型 | 按 error_type 分类计数，并辅助报告 finish_reason=length 等已记录证据 |

latency_ms 是服务现有计时区间：从 running 证据提交后开始，包含模型调用、解析、安全检查、规则评分及业务对象准备，成功时在最终提交前停止。因此它不是纯 API 响应时间，也不是包含所有写库时间的完整端到端耗时。不能用 started_at/finished_at 相减或页面刷新耗时替代后声称口径相同。

Token 必须来自实际 SDK usage；NULL 表示未返回或不可用，不等于 0，不用 input_chars/output_chars 推算。总消耗包含已有 usage 的失败尝试，每项报告已知记录数和缺失数；有缺失时称“已知 Token 总量”，不能声称全部消耗已统计。不据 Token 直接推断货币费用。

当前持久化错误类别包括 AIConfigurationError、AIResponseError、AIReviewDisabledError、WorkflowPersistenceError、AIProviderError。其中 Provider 异常归并较粗，不能仅凭 AIProviderError 区分超时、限流或连接失败，不能仅凭 AIResponseError 区分所有 Schema 与安全失败。finish_reason=length 可支持截断分类，其余按现有证据报告。

输入校验、模型配置或初始证据保存失败可能发生在 Run 创建之前，后续实验清单记录为“调用前失败/未开始”，不伪造 GenerationRun。未终结 running 单列，不擅自改库将其归为 failed。

Baseline 可离线记录其实际响应 model、usage 和调用状态，但普通文本可读取与 Proposed 的校验并落库成功含义不同；两组成功率不直接当作相同定义相减。RQ3 以 Proposed 工程表现为主，若只获得 Baseline API 调用耗时，不与上述服务 latency_ms 进行速度优劣比较。

method、requirement_id、attempt_no、实验批次和人工质量分属于**离线实验关联字段**，当前模型没有这些专用字段，不在本轮新增。Proposed 的模型等源字段保留 GenerationRun 原值；requested_model/returned_model 分开记录。returned_model 没有独立证据时保持 null，model_evidence_source 注明来源不明，不能只凭 provider_model 回退值推断是否真的收到响应标识。

覆盖记录的 content_stage 固定为 initial 或 final_accepted，分别表示初始用例集合与最终接受集合。保留两名评价者的 original 判断行及讨论后的 adjudicated 裁定行，以阶段、参考点、评价者和判断类型区分记录，不覆盖初判。指标只按最终裁定的不同参考点计数；同一参考点被多条用例命中仍计一次。人工评分表也注明 initial 阶段，防止与修改后评价混用。

仅保存虚构需求、用例内容和安全元数据，不保存凭据、请求头、SDK 原始异常、环境变量转储、业务日志或推理过程。不导出内部完整系统 Prompt；用版本/hash 及源码版本追溯，baseline-v1 的公开实验模板在本方案中给出。

## 9. 人工评价方案

### 9.1 人员安排

拟安排 2 名具备基础软件测试知识的评价人员，例如论文作者与一名学习过软件测试课程的同学。两人都独立完成覆盖判断和 10 分制评分，不将其描述为行业专家评价。

主审核由同一名人员完成两组的修改、接受和拒绝，另一人复核争议及明显不一致，避免两组因审核人不同产生系统差异。Proposed 主审核者使用真实登录账号操作，评价导出使用代号。

### 9.2 执行顺序与统一标准

1. 在生成前确认需求及参考点，冻结评分和接受标准。
2. 使用不计入主实验的评分说明进行规则培训；本轮不制作或运行训练样本。
3. 对初始输出作无语义补充的统一展示，随机排列匿名批次，不显示方法、模型、规则分或审核结论。评价者查看相同需求、参考点和九字段内容。
4. 两人独立评分并记录覆盖依据，提交评分前不交流方法表现。
5. 汇总人工分，记录分歧；覆盖分歧通过对应需求和用例文本讨论形成一致结论，保留双方初始判断。单项评分相差 2 分或总分相差至少 3 分时复核是否误读规则，保留修改理由，不为某组得高分而协商。
6. 质量评价完成后再进行内容审核。主审核者交替处理两组，不先完成整组再完成另一组；按统一标准修改或拒绝，第二人复核争议。

接受标准为：目标符合需求，前提与步骤足以执行，预期可判断且正确，没有明显重复或虚构业务规则，并满足第 5.2 节统一字段规范和编号唯一性。无需补改内容即可接受的记直接接受；保留原测试目标且可通过字段修正达到标准的先修改后接受；目标无关、严重冲突、需要重新编写测试目标或无可靠修复依据的拒绝。接受不意味着该用例已执行或对应业务已验证。

不为了“覆盖所有参考点”强行接受有问题的用例，也不通过给某一组额外新增用例提高其接受率。两组初始输出中已有的重复用例保留为评价对象，冗余用例按同一拒绝规则处理。

### 9.3 偏差控制与后评估

统一展示应保留所有初始用例和缺失字段，不隐藏 Proposed 或 Baseline 的缺陷；将测试点分析、系统分数和方法标签与主要用例盲评隔离。文本风格可能仍透露方法来源，应在限制中说明无法保证完全盲法。

人工审核阶段需要使用 Proposed 页面，无法维持完全盲法。记录其规则分提示可能影响判断的限制，要求接受与拒绝必须依据需求和统一标准，不用“规则分高”替代审核。

审核后可按同一参考清单评价两组**最终接受用例集合**的覆盖率，观察审核后的可用结果；与各自初始覆盖率并列展示。不能把 Proposed 的修改后结果与 Baseline 的修改前结果比较，也不能将人工补改后的提升全部归因于模型或结构化 Prompt。

## 10. 结果分析、风险与限制

### 10.1 分析方式

RQ1 按需求计算 Proposed−Baseline 的覆盖率及人工分差值，报告配对样本数、均值、中位数和“提高/相同/降低”的需求数量。覆盖率差值用百分点表示；人工评分差值用分表示。按七类需求汇总，避免总体均值掩盖某类需求的下降。

RQ2 对比两组的修改率、字段变化、直接接受率和拒绝率，同时给出分母、最终接受数量及最终覆盖率。可按需求列出整理负担差异；不把少量字段变化等同于少量工作时间，也不因丢弃困难用例而宣布成本降低。

RQ3 报告调用状态数量、成功率、成功/失败耗时、已知 Token 消耗及缺失比例、失败类别。结合质量结果说明新增约束与输入长度的代价，允许出现质量改善但耗时或 Token 上升的情况。

不预设 Proposed 必须胜出，不使用复杂显著性检验，也不把“均值较高”表述为“已证明显著优于”。若两组接近或 Proposed 某项更差，同样报告，并按可追溯的虚构案例分析原因。正式结果表在执行后填写，本文件不预填任何实验得分、接受率或成功率。

### 10.2 风险与限制

- **规模和代表性有限。** 28 条人工虚构需求覆盖常见规则，难以代表大型系统、复杂领域或长期项目。
- **人工评价有主观性。** 两名评价者及统一规则可减少偏差，仍不能消除作者参与、经验差异和来源识别的影响。
- **单一模型。** 两组使用同一 DeepSeek 模型，结论不推广到全部模型，也不证明模型优于人工。
- **响应模型来源限制。** 现有 Run 的模型字段包含配置回退，若未另行采集响应元数据，只能确认两组请求配置一致，不能声称逐次验证了服务端返回标识。
- **随机性与服务波动。** 每需求每方法只生成一次，且未固定模型随机种子；交替顺序只能部分缓解时间和网络影响，不证明重复稳定性。
- **复合方法比较。** Prompt、JSON/Schema、规则评分与审核工作流一起构成系统方法；没有消融实验，不能分别量化每个机制的独立贡献。
- **规则分与语义质量不同。** 形式满足、场景标签齐全和可观察词存在不保证正确；实际需求覆盖依赖独立人工判断。
- **修改字段是粗粒度代理。** 修改一句话和重写整个步骤字段都计 1，不能准确反映编辑长度、认知负担或时间成本。
- **无真实业务执行。** 评价的是用例文本的可执行性，不测故障发现率、缺陷检出率或被测系统真实代码覆盖率。项目的 95.14% 行覆盖率属于系统自身回归，不能作为生成用例的场景覆盖率。
- **失败与缺失证据。** 部分错误类型归并，Token 可缺失，进程终止可能留下 running；必须报告缺失和未终结记录，不能只展示成功样本。
- **审核后结果混有人工作用。** 最终用例质量不能全部归因于 LLM；审核记录证明过程可追溯，收益还需要初始与最终结果支持。

| 第 7 章：实验结果分析 | 7.1 场景覆盖与人工质量评价 | 执行后回答 RQ1，不在方案阶段写结论 |
| 同上 | 7.2 人工修改负担分析 | 执行后回答 RQ2 |
| 同上 | 7.3 工程表现、失败与适用限制 | 执行后回答 RQ3，并讨论第 10 节限制 |

论文的“系统已实现”“实验拟采用”和“实验结果表明”分别对应源码/验收证据、方案和实测结果。只有完成正式采集和评价之后，才能使用第三种表述。

## 12. 后续实验工作与完成边界

### 12.1 后续需要准备或完成的内容

1. **数据与评价准备：** 编写并复核 28 条虚构需求和 168 个参考场景点，冻结数据版本、评分表、接受标准与运行清单。
2. **Baseline 采集准备：** 按 baseline-v1 建立独立的单次调用及安全保存方式；保留模型、实际 usage 和初始输出。当前系统没有这一实验入口。
3. **导出与离线关联：** 建立现有 GenerationRun/Draft/ReviewRecord 的只读导出方式，并用文件关联需求 ID、方法及评价编号；可人工整理或另行编写辅助工具，不要求新增业务模型、API 或前端。如需逐次确认返回模型，另在实验侧准备安全响应元数据采集；否则保留来源不明标记，不虚构证据。
4. **人工评价与统计：** 准备匿名评价表及 Baseline 审核事件表，计算覆盖率、10 分制评分和直接接受率等派生指标，核对现有修改字段统计口径。
5. **正式执行与论文分析：** 在后续明确开展实验时，按冻结方案运行两组、完成审核、检查证据和分母，再填写结果与讨论。

这些是后续实验准备和采集任务，不是本轮实施范围。该方案可以利用现有生成与审核能力加离线文件完成，不需要为实验新增数据库实体或更改业务生成流程。

### 12.2 设计自检与证据边界

| 自检问题 | 当前回答 |
| --- | --- |
| 是否夸大贡献？ | 只研究辅助价值，不主张模型优于人工或所有方法；效果待实验验证 |
| 是否能够理解并复核？ | 已明确样本、方法、评分、分母、失败处理及关联字段；数据尚待制作 |
| 实验是否公平？ | 固定同模型、输入、调用预算和评价；主比较使用初始输出，方法组合差异已说明 |
| 评价是否完整？ | 同时记录覆盖、人工分、修改与拒绝、工程失败；时间成本和真实业务执行不作测量 |
| 方法描述是否符合实现？ | 单次联合生成、Schema/规则评分、现有实体及审核流程均按源码核对；Baseline 与离线工具列为计划 |
